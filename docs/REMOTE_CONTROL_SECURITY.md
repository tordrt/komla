# Remote control security

Remote control is a remote shell. Its security boundary is therefore the authenticated encrypted path between a trusted browser and the Komla desktop, not merely possession of a reachable URL.

## Supported transport

Komla serves the remote web application and WebSocket API from a localhost-only server. A phone reaches it either on the same machine for development or through the user's private Tailscale network using Tailscale Serve. Komla has no hosted relay path.

Tailscale supplies network reachability and HTTPS. The Komla protocol separately authenticates both endpoints and encrypts application frames, so a transport intermediary cannot create, replay, reorder, or drop terminal input without ending the session.

When Komla manages the Tailscale Serve route, it removes the route when Komla quits and restores it at the next launch, so no other program can take the local port while Komla is closed. If removing it fails when remote control is turned off, Komla tries again at the next launch and quit. Whenever Komla configures or restores that route, it first checks Tailscale Funnel, and it does not run remote control while Funnel is on for that HTTPS port.

## Identities

The desktop retains its existing installation signing key. Its SHA-256 fingerprint is authenticated during the ephemeral P-256 ECDH handshake.

Each trusted browser has two independent credentials:

1. A non-exportable P-256 device key generated by WebCrypto and stored in IndexedDB.
2. A WebAuthn passkey registered with user verification required.

The registry binds the browser device-key identifier, public key, exact passkey credential ID, RP ID, and origin in one versioned record.

## Enrollment

The desktop creates a 256-bit random secret and places it in the QR URL fragment. URL fragments do not enter HTTP request paths or access logs.

After the encrypted Peer handshake:

1. The browser sends the one-time secret, its device public key, and a proposed label.
2. The desktop checks the secret and derives the device ID from the public key.
3. The desktop issues a WebAuthn registration challenge for that device ID.
4. The browser completes user-verified WebAuthn registration and signs a domain-separated proof containing the challenge and encrypted-channel binding.
5. The desktop verifies both proofs before persisting the trusted device.

Enrollment only creates a trusted-device record. It deliberately closes that connection; shell access begins only after a fresh reconnect ceremony.

## Reconnect

The browser loads its device key from IndexedDB and identifies the matching registry record. The desktop returns only that record's passkey credential ID. The browser must:

- complete WebAuthn authentication with user verification required, over a hash of the challenge and current channel binding; and
- sign a separate device proof over the authentication challenge and current channel binding.

Only after both checks succeed does Komla attach the authenticated Peer to the remote shell session.

A browser that isn't paired, such as a private window or another browser on a phone whose passkey
syncs, signs in with a passkey alone (ADR 0007). It makes a non-exportable P-256 key of its own and
sends its public key in the hello. The desktop asks for any passkey without naming one, accepts an
assertion only from a passkey in its registry for this RP ID and origin, and requires a proof by the
browser's new key over the authentication challenge and channel binding. The browser keeps that key
in IndexedDB; the desktop doesn't store it, so the browser signs in that way again whenever no
resume grant is left. Removing the passkey's record ends every browser signed in with it.

After successful user verification, the desktop may issue a rotating resumption grant. The grant
works for the window set in Settings → Remote → "Ask for passkey again after" (5 minutes, 15 by
default, 1 hour or 8 hours) after the connection that received it ends, and never more than eight
hours after the device last passed passkey verification; a silent resume carries that time forward
instead of renewing it. It also works while that connection still looks open after a silent network
drop, and signing in with it then replaces that connection, so a grant never yields a second
session. The browser keeps the grant in its origin's `localStorage`, so a Home Screen app the
system closed, a reload or a new tab resumes too; the desktop keeps it in memory. It must be combined
with a fresh installation-key signature over a new challenge and encrypted-channel binding, and it
is used up only once that signature verifies: an attempt that drops before then leaves it for the
next one. A grant names the browser key that must sign and the passkey it descends from, so it
resumes only that browser, and only while that passkey is still trusted, and of two attempts with the same grant only the first to verify signs in. This lets the
app come back after a phone sleeps or a network drops without invoking the passkey again. Expiry,
replay, a desktop restart, device removal, disconnecting the device from the desktop, or turning
remote access off falls back to fresh passkey verification. SSH hosts apply the same window, which
the desktop writes into their `trust.json`.

The browser asks for the passkey only inside a tap (an Unlock button), or right after one, since
Safari shows no passkey sheet for a request that doesn't follow a tap. The desktop and hosts wait two
minutes for the passkey response, and a failed or cancelled request can be retried against the same
challenge while they wait.

One trusted device uses remote control at a time. A newer completed sign-in, of the same device or
another, replaces the older connection, which is closed with a code telling it not to reconnect.
Another device's connection lets go of its size leases at once.

Each browser installation pairs with its own passkey, so registration excludes no existing
credential: an iPhone's Safari and its Home Screen app share synced passkeys but not storage, and
each needs a key and passkey of its own.

## Terminal presentation

The desktop maintains a headless terminal model for each live PTY generation. Remote attachment
sends a serialized screen and scrollback in bounded encrypted chunks, followed by ordered output.
A generation change resets the browser terminal before restarted-process output is accepted.
Output is batched briefly before encryption. Every frame is sized by its encoded bytes before it
takes a sequence number: output and workspace lists too large for one frame are split, and any other
frame too large fails alone without ending the session. When too much is still waiting to reach the browser,
the desktop skips new output instead of queueing it, and once the backlog drains it resets the
browser terminal to the current screen. A browser that reconnects keeps its screen and asks for the
output after the last frame it applied; the desktop sends only that when it still holds all of it
at the terminal's current size, and a snapshot otherwise.

The PTY has exactly one size authority. Electron owns it normally; an attached authenticated phone
may take a size-authority lease. Electron renders the same canonical dimensions while that lease is
active, and the latest desktop dimensions are restored on detach, or when the phone stops the
workspace. A key or press in the terminal on the desktop takes the size back without ending the
lease (xterm's own replies to the program don't count), and the desktop tells the phone, which then
shows the desktop's dimensions scaled down; the phone's next resize takes the size again. When the
phone's connection drops,
its lease is kept for a minute for that device's reconnect; another device's attach, removing the
device, or turning remote access off releases it at once.

## Installed app

The phone client can be added to the Home Screen. Its service worker, scoped to `/remote/`, caches only the public app shell (the page, its assets, the manifest and icons) so an installed app can open and report that the desktop is unreachable. It asks the desktop first on every load and never handles `/remote/ws`, `/remote/config` or `/remote/health`. It holds no credentials: the browser installation key stays in IndexedDB and every session still authenticates with the desktop. The desktop serves the worker and manifest with `cache-control: no-cache`, so a Komla update replaces them.

## Notifications

A trusted device can opt in to Web Push for attention that needs it: input required, turn complete and error. The desktop sends each notification straight to that browser's push service (Apple, Google or Mozilla); Komla operates no gateway.

- The desktop signs requests with a per-install VAPID key pair (RFC 8292). It is encrypted at rest with `safeStorage`, never shared between installs, and created only when a phone asks for it. Without real secure storage, notifications are unavailable. A key the keychain refuses to decrypt, as after a dismissed prompt, is kept with its subscriptions and read again later; only an unreadable key file is replaced.
- Every payload is encrypted to the subscription's keys (RFC 8291), so the push service relays ciphertext. It still sees the endpoint, the payload size, the time and the urgency.
- A payload holds the workspace title, the attention label with a short message (at most 180 characters) and the workspace and terminal ids. It never contains terminal output. The phone shows it on its lock screen.
- Subscriptions live in `remote-push-subscriptions.json`, keyed by the trusted device's passkey credential. One is accepted only from an authenticated session of that device, removing the device deletes it, and a push service's 404 or 410 deletes it too.
- A push opens the app; it grants nothing. Opening a workspace from one still needs an authenticated session.

## SSH hosts

A phone can also open an SSH host directly, through the Remote Companion on that host (ADR 0005), so it keeps working while the desktop sleeps or would need a new SSH login.

- The host server listens on `127.0.0.1` only and is published with Tailscale Serve on the host. Before publishing it, the desktop checks Tailscale Funnel for that port on the host and stops the server if Funnel is on.
- It speaks the same protocol. The host signs the handshake with its own key, kept in `identity.json` with mode 600; anyone who can read that file can already run the host user's shells. The phone pins the key's fingerprint, which the desktop gave it over an authenticated session.
- Only the desktop decides trust. Over an SSH connection it already has open (it never logs in just for this), it writes `trust.json` with each trusted phone's installation key, exact passkey credential (as SPKI, ES256 only), RP ID and origin, under a seven-day lease that every connection renews. Hosts never enroll devices.
- A phone signs in to a host as it does to the desktop: a user-verified passkey assertion for the desktop's RP ID and origin, which the host verifies itself, plus an installation-key proof over the host's channel binding, or a host-issued resume grant under the same rules. A browser that isn't paired signs in with any passkey in `trust.json` for the upgrade's origin and a proof by its own key, as on the desktop. WebSocket upgrades must come from a trusted phone's origin.
- A signed-in phone can list the host's workspaces and attach a tmux client to an existing `komla-<terminal>` session. It can also create workspaces, start and stop them, and open and close tabs, but it only names what to start: projects, agents and launch modes come from `launch.json`, which the desktop writes next to `trust.json` over the same connection, and a workspace starts again with the agent commands Komla saved in its manifest. Its prompt reaches the agent command shell-quoted, and every path stays inside Komla's data directory on the host. A shell tab adds nothing a signed-in phone couldn't already type into an agent's terminal.
- Removing a phone, or turning remote control off, reaches a host the next time the desktop connects to it; the lease bounds how long an unreachable host keeps honoring a removed phone. A host ends a phone's session as soon as it reads a trust file without that phone.

## Transcript and key binding

Handshake signatures and the session-key derivation use a domain-separated, length-prefixed transcript. Both peers hash the same transcript to obtain the channel binding. Device proofs include that binding, and so does what a passkey signs: the page asks for a signature over a hash of the endpoint's challenge and the binding, never over a challenge as sent. That prevents a valid passkey or device signature from being replayed into another encrypted session, including an SSH host passing on to the desktop a signature it asked a phone for.

## Protocol features

Optional features are negotiated after the handshake: the browser lists the capabilities it
supports in its hello, and the endpoint names in its reply the ones it will use. Neither side uses a
feature the other did not list. Frame schemas stay strict, so anything a newer peer might send is
behind a capability first.

- **Binary frames:** the same sequence number, nonce and AES-GCM ciphertext as a text frame, without
  the JSON and base64 around them, and terminal output and input as binary payloads. Text and binary
  frames share one sequence counter, so a gap or repeat across the two still ends the session.
- **App build:** the desktop names the phone app build it serves. A page running another build, for
  example one left open across a Komla update, reloads before it uses the session.

## Security invariants

- Remote control is off until the user turns it on in Settings → Remote; until then Komla starts no
  server and changes no Tailscale configuration.
- The local server never binds a wildcard network address.
- Public browser origins must be HTTPS; localhost is the development exception.
- WebSocket upgrades must come from the origin Komla serves: its Tailscale origin or its localhost origin.
- Komla does not configure, restore, or start remote control while Tailscale Funnel is on for its HTTPS port.
- Pairing secrets are single-offer, high-entropy values and expire. Each offer enrolls at most one device.
- Encrypted frames carry consecutive per-direction sequence numbers; any gap or repeat ends the session.
- Registration and authentication require WebAuthn user verification.
- A trusted passkey signs in, with user verification, from any browser of its origin. The
  browser's key, its installation key or one it made to sign in, signs the session.
- A browser key alone is insufficient without a trusted passkey or a still-valid grant created by
  its recent verification, and a grant resumes only the browser whose key it names.
- Silent resumption requires both a recent single-use grant and a fresh transcript-bound device-key
  signature; the grant alone cannot authorize terminal access.
- Removing a trusted device disconnects its active session before deleting its registry record.
- The service worker caches only the public app shell and never handles the WebSocket or connection routes.
- Push payloads are encrypted to the subscription and never carry terminal output; the VAPID private key never leaves `safeStorage` unencrypted on disk.
- Only a trusted device's own authenticated session can create or remove its push subscription, and removing the device removes it.
- With "Allow access to this computer" off, a device gets no workspace or terminal that runs on the
  desktop (a local workspace or an SSH workspace's Local copy shell): they are left out of lists, refused
  when named, and detached at once when the setting turns off, and their attention neither shows nor
  pushes. A Terminal Command the project would run in the Local copy is refused. Setup steps the
  project sends to the Local copy still run when a device creates or starts an SSH workspace; their
  terminals stay hidden from it. Pairing and the host list still work.
- An SSH host's phone server binds only `127.0.0.1`, does not run while Tailscale Funnel is on for its port (the desktop checks before starting it), closes a connection that doesn't start signing in within a minute of opening, never enrolls a device, and trusts only the phones in the desktop's current trust file, and none once its lease has expired.
